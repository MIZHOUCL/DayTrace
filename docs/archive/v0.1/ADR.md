# Daytrace 关键技术决策记录

## ADR-001：默认只扫描用户选择的工作区

状态：Accepted

决策：用户必须明确选择工作目录；不支持默认全盘扫描。

原因：全盘扫描会造成隐私、性能和误报问题，也不符合“日志助手”而不是“监控软件”的定位。

## ADR-002：扫描与读取分离

状态：Accepted

决策：元数据扫描、结构分析、diff 读取和正文读取分成独立权限级别。

原因：文件发生变化不等于系统获得读取文件正文的授权。分离后可以降低 token 使用和隐私风险。

## ADR-003：Graph View 默认按模块聚合

状态：Accepted

决策：默认展示项目、模块、变化集合、日志和 Codex 会话；文件节点按需展开。

原因：文件级节点很容易导致图谱过载，用户真正关心的是项目工作结构和关系。

## ADR-004：Codex 深度链接先作为引用

状态：Accepted

决策：`codex://threads/<id>` 在核心系统中只解析为会话引用。内容导入通过用户粘贴/导出、浏览器扩展或正式接口 provider 完成。

原因：深度链接是资源定位符，不等于第三方可读取的会话正文 API。核心功能不能依赖未公开的内部接口或本地文件格式。

## ADR-005：AI Provider 采用适配器接口

状态：Accepted

决策：核心只依赖 `summarize()`、`estimateTokens()`、`capabilities()` 等接口，不绑定具体模型名称。

原因：用户需要 OpenAI、兼容接口、本地模型和无 AI 模式；供应商和模型能力会变化。

## ADR-006：事实与表达分离

状态：Accepted

决策：先生成带来源的事实对象，再生成可编辑的日志文字。

原因：这样可以追溯来源、重新生成不同风格、区分用户确认和 AI 推断，降低幻觉风险。

## ADR-007：预算超限时失败安全

状态：Accepted

决策：估算失败、预算不足、脱敏失败或 provider 能力不明时，不自动发起云端请求。

原因：token 成本和数据外发都属于用户可感知风险，宁可中止并让用户选择降级策略。

## ADR-008：本地 SQLite 作为 MVP 存储

状态：Accepted

决策：MVP 使用 SQLite + FTS5，不引入服务端数据库。

原因：项目是个人日志工具，本地存储能降低部署复杂度、隐私风险和运行成本；图谱关系规模也适合关系表。

## ADR-009：第一版不加入行为监控功能

状态：Accepted

决策：不做键盘记录、全量浏览器历史、后台截图、录音和隐蔽进程采集。

原因：这些能力会改变产品性质，增加合规与安全风险，也不是生成可信工作日志所必需的。

## ADR-010：官方能力不明确时保留不确定性

状态：Accepted

决策：产品文档和 UI 不把未验证的 Codex 读取能力描述成已支持功能；使用 capability 状态和实验性标识。

原因：官方 OpenAI 文档当前未能通过本次文档访问验证深度链接的第三方读取协议，因此规划只承诺引用和用户主动导入。
